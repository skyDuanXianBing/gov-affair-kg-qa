> 依据：《论文/》7 篇 KG 论文启示 + 本仓库试点实证（`kg/pilot/`）+ `进度安排.md` 提出的问题。

## 一、论文对建 schema 的启示（只讲 schema 视角）

| 论文 | 启示 | 本方案落点 |
|---|---|---|
| Wikontic | schema 从权威源派生而非凭空设计；域-值域约束表；isA 层级下传；别名向量索引；本体错位率监控（仅 3.5%） | §3.3 约束校验层、§3.1 别名属性 |
| SocraticKG | 受理条件等复杂逻辑不适合硬塞固定 schema，先 5W1H 展开再抽；但完全无 schema 不可接受（政务要可追溯）→ 混合式 | §3.2 ServiceCondition + 开放命题 |
| SynthKG | schema 只约束骨架，长文本细节用"命题"承接（保留金额/时限/条款号），避免 schema 无限膨胀；命题谓词保持开放 | §3.2 Proposition |
| QSRAG | 检索打分靠"问题 × 关系类型"交互，前提是关系命名有语义区分度（隶属/管辖/协办必须分开） | §3.1 关系命名冻结 |
| HotpotQA | 先想"哪些实体适合当多跳桥"；过滤无信息量节点 | §3.1 Department 隶属层级桥 |
| AutoGraph-R1 | "图上推理"要关系丰富连通，"定位原文"要精简干净——政务两者都要，schema 给两条路留接口 | 结构化边支撑推理 + Chunk/命题边支撑溯源 |

## 二、抽取路线决策（对应《进度安排.md》问题 4.1 / 4.2）

### 4.1 论文框架移植 OpenSPG，还是原生抽取？

**结论：骨架原生 + 抽取自建，不魔改 OpenSPG 内核。**

- OpenSPG「新增知识」界面（截图 `image.png`）是 GraphRAG 式黑盒流水线：分段长度 500、六种固定索引管理器，分段策略/prompt/约束校验均不可控——无法实现论文要求的"去语境化 + 5W1H 展开 + 命题抽取 + 域值域校验"。
- OpenSPG 的**存储与导入层**（SPG MarkLang schema、SPGTypeMapping/RelationMapping、向量索引、Cypher）已在试点验证 100% 对账（`kg/pilot/`），继续原生使用。
- 抽取逻辑自建 Python 脚本（调 LLM API），产物仍是 CSV，走同一条已验证的导入管线——论文方法的核心是 prompt 与流水线编排，自建可逐字复现且全程可审计。

### 4.2 不同数据如何选抽取方案（按字段形态分流）

| 数据形态 | 例子 | 方案 |
|---|---|---|
| 结构化字段（已规整） | 事项名、部门、材料清单、文号、编码 | 规则 mapping（现有 `kg/build/adapter.py`，零 LLM 成本，已验证） |
| 半结构化长文本 | 受理条件、窗口/网上流程、法条全文、审查标准 | LLM 命题抽取（SynthKG 流水线 + SocraticKG 5W1H 展开） |
| 天然 QA 对 | 常见问答 FAQ 字段 | 直接转 Chunk/FAQ，不浪费 |

## 三、Schema v0.3 设计

核心思路：**双层 schema——骨架层封闭强约束（规则建图），知识层开放挂接（LLM 抽取），两层通过命题与 Chunk 连接。**

保留 v0.2 全部 8 实体 + 4 概念。v0.2 有两个试点实证的设计必须继承：

1. **LegalCitation 条款级弱实体**（id = `LC-`+md5(文号|条款)）：解决 (s,p,o) upsert 下的 79% 条款边塌缩、86% 条文冲突；
2. **共享节点 + 边属性承载上下文**（Material 节点只放名称，份数/必要性等放 requireMaterial 边属性）。

### 3.1 骨架层增量（四处变更）

| 变更 | 内容 | 依据 |
|---|---|---|
| + Department 隶属层级 | `ImplementingOrg -[belongsTo]-> ImplementingOrg`，从部门名解析"省→市→县"隶属链。多跳刚需：当前"该部门的上级主管单位发布了哪些事项"无边可走 | HotpotQA 桥接实体 |
| + 别名属性 | ImplementingOrg / Material / LegalBasis 各加 `alias(别名): Text, MultiValue`；导入前过别名归一表（"市发改委"="发展和改革委员会"；同义材料合并；同一法规多文号版本归一） | Wikontic 实体规范化 |
| + 法规类型层级 | LegalBasis 加 `legalType`（法律/行政法规/地方性法规/部门规章/规范性文件）+ 发布机关、生效日期属性 | Wikontic 类型层级 |
| 关系命名冻结 | 现有 8 种关系保持动词化互斥命名；新增关系同标准：belongsTo / hasCondition / hasChunk / statesProposition / extractedFrom | QSRAG 关系区分度 |

### 3.2 知识层（新增实体）

```
Chunk(文本块): EntityType
    properties:
        content(内容): Text          index: TextAndVector
        source(所属节点): Text        # = 骨架节点 id（事项编码/文号），双向溯源锚点
        sourceField(来源字段): Text    # acceptCondition / windowProcess / legalContent…
        chunkIndex(序号): Integer

Proposition(命题): EntityType       # SynthKG 命题层，开放三元组的载体
    properties:
        subject(主体): Text
        predicate(谓词): Text        # 开放，不进白名单
        object(客体): Text
        statement(自然语言陈述): Text  # 原文改写的完整句子，检索与溯源单元
        source(所属节点): Text
    relations:
        extractedFrom(抽取自): Chunk

ServiceCondition(受理条件): EntityType  # SocraticKG 5W1H 展开的产物
    properties:
        conditionType(条件类型): Text  # 申请对象 / 情形 / 数量限制 / 禁止情形…
        statement(条件陈述): Text
        source(所属节点): Text
```

骨架实体挂接关系（Affair / LegalCitation / ImplementingOrg 均加）：

```
hasChunk(原文块): Chunk
statesProposition(事实命题): Proposition
Affair 专有: hasCondition(受理条件): ServiceCondition
```

关键设计判断：

- **命题谓词保持开放、不进 schema 白名单**（SynthKG/SocraticKG 实证：强塞封闭关系表会丢信息）；schema 只约束命题"挂在哪个骨架节点下"，保证溯源。
- **受理条件升为实体**：高频参与多跳推理（"什么人能办什么"）。
- **FAQ 暂不建实体**：数据 89% 为空，放 Chunk 层。

### 3.3 约束校验层（Wikontic 方法，纯脚本）

约束表 `kg/design/constraints.csv`，逐关系定义域-值域，由 `scripts/validate_openspg_csvs.py` 消费：

```csv
关系,主体类型,客体类型,校验规则
implementedBy,Affair,ImplementingOrg,客体必须存在于部门表
belongsTo,ImplementingOrg,ImplementingOrg,禁自环;层级只能 省→市→县
hasChunk,Affair|LegalCitation|ImplementingOrg,Chunk,chunk.source 必须等于主体 id
citeLegal,Affair,LegalCitation,客体 partOf 必须指向存在的 LegalBasis
```

**违例不删、打标进人工审核队列，输出"本体错位率"指标**——建图质量 dashboard 第一个指标，也是论文可引用的实验数据。

## 四、落地步骤（对应《进度安排.md》第 3→5 条）

1. **写 v0.3 schema 文件**：以 `kg/design/GovAffair.schema` 为底加增量；
2. **建三张别名归一表**（部门/材料/法规）：规则 + LLM 批处理生成候选对，人工确认，先跑 1 万条试点；
3. **写抽取脚本** `scripts/extract_propositions.py`：分块（复用 `scripts/chunk_openspg_documents.py`）→ 去语境化（prompt 把"本机关/该事项/申请人"替换为规范全称）→ 5W1H 展开（针对 acceptCondition）→ 抽命题+三元组 → 输出 Chunk/Proposition/ServiceCondition 三张 CSV → 现有导入管线；
4. **试点重灌 1 万条 + 对账**：沿用 pilot 对账方法，新增指标——命题覆盖率、本体错位率、别名合并数；
5. **qa/ 白名单扩容**：`qa/multihop.py` REL_INFO 从 8 种扩到含 belongsTo/hasCondition/hasChunk 的 12 种，locate 支持绑定 Chunk。

## 五、刻意不做的事

- **不做完整领域本体**（不建几百类的"办事指南本体"树）：SynthKG 证明骨架 + 开放命题够用；事后可从命题谓词统计归纳本体（HotpotQA 事后统计法）；
- **不动 OpenSPG 内核**：「新增知识」UI 流程整条不用，只用 schema/导入/存储层；
- **FAQ 不建实体**：89% 为空，试点阶段放 Chunk 层。

---

**一句话总结：schema = 旧骨架（已验证）+ 部门层级桥（多跳刚需）+ 命题/Chunk 开放层（论文方法落点）+ 约束校验表（质量保障）；抽取自建脚本、导入走原生 OpenSPG、不魔改框架。**
