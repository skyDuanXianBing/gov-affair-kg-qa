# 知识建模方案 v0.3 修订版：稳定骨架、证据层与开放知识层

> 本文是政务服务知识图谱的 Schema 设计方案，不是数据导入 manifest，也不是 LLM 抽取脚本。
>
> **目标 Namespace：** `ZwdmxGJ`
> **核心实体：** `GovernmentService`
> **数据来源：** `dataset/pilot/`、`dataset/personal/`
> **修订日期：** 2026-08-28
> **前置文档：** `docs/知识建模方案-v0.3.md`
>
> 本版本吸收 Wikontic、SocraticKG、SynthKG 的建图思想，并以当前 CSV 数据结构和已有试点结果为约束。本文不再使用 dev 项目旧版 `GovAffair/Affair` 命名；后续 Schema、CSV、导入 manifest 和 QA 查询统一使用本文定义的 `ZwdmxGJ` 模型。

---

## 一、设计结论

本项目采用三层设计：

```text
稳定骨架层：固定实体、固定关系、强约束、规则导入
        ↓
证据层：Chunk、来源、字段、行号、版本
        ↓
开放知识层：Proposition、LLM 抽取结果、置信度、审核状态
```

核心原则：

1. **结构化字段优先规则建图，不使用 LLM 替代确定性 Mapping。**
2. **高频、稳定、需要精确查询的事实进入固定 Schema。**
3. **复杂长文本先分块和去语境化，再抽取命题。**
4. **命题的谓词保持开放，不为每个长尾谓词修改 Schema。**
5. **所有抽取结果必须能够回溯到 Chunk 和原始来源。**
6. **实体归一和关系域值域校验在进入图谱前执行。**
7. **Schema 设计必须从业务问题和数据画像出发，而不是从论文术语直接复制。**

## 三、论文方法如何落到 Schema

### 3.1 Wikontic：约束、归一与质量控制

Wikontic 对本项目的落点不是照搬 Wikidata，而是建立三种约束：

```text
实体类型约束
关系域和值域约束
实体归一和别名约束
```

例如：

```text
GovernmentService --handledBy--> Department
GovernmentService --requiresMaterial--> Material
GovernmentService --citesLegal--> LegalCitation
LegalCitation --partOf--> LegalBasis
```

以下事实不能进入图谱：

```text
Department --requiresMaterial--> LegalBasis
Material --handledBy--> GovernmentService
GovernmentService --partOf--> Department
```

Wikontic 的实体归一思想落为外部归一表，而不是一开始仅增加 `alias` 属性：

```text
entity_aliases.csv
```

归一表至少记录：

```text
entity_type
raw_name
canonical_id
canonical_name
normalization_rule
confidence
review_status
source
```

### 3.2 SocraticKG：复杂条件的结构化

受理条件、资格要求、限制情形和例外规则经常以长句或条件句出现，不能只依赖直接三元组抽取。

建议流程：

```text
原始长文本
    ↓
按字段和语义边界分块
    ↓
5W1H 问题展开
    ↓
上下文独立的条件陈述
    ↓
ServiceCondition / Proposition
    ↓
关系约束和来源校验
```

例如原文：

```text
符合有关条件的申请人，可以向本机关提出申请。
```

应至少得到：

```text
条件主体：申请人
条件内容：符合有关条件
允许动作：提出申请
申请对象：当前政务事项
办理机关：当前事项主管机关
```

但抽取结果仍然必须保留原始文本，不能只保存 LLM 改写结果。

### 3.3 SynthKG：长文本的开放命题层

SynthKG 对本项目的核心启示是：

```text
固定 Schema 负责骨架
Proposition 负责开放事实
Chunk 负责原文证据
```

因此，不为每一个新谓词增加关系。例如以下长尾知识不直接扩展 Schema：

```text
申请资格
禁止情形
特殊办理要求
补充材料条件
适用例外
办理地点限制
```

而是保存为：

```text
Proposition.predicate
```

这能避免 Schema 无限膨胀，同时保留事实内容。

## 四、Schema 分层设计

## 4.1 稳定骨架层

### GovernmentService

政务服务事项，是图谱的核心实体。

建议属性：

```text
name
serviceId
categoryL1
categoryL2
departmentName
departmentCode
publishDate
versionDate
serviceStatus
onlineDepth
onlineAvailable
promiseTimeLimit
legalTimeLimit
officialListCount
sourceUrl
sourceFile
sourceLine
```

核心关系：

```text
handledBy -> Department
collaboratesWith -> Department
requiresMaterial -> Material
hasCondition -> ServiceCondition
hasProcessStep -> ProcessStep
producesResult -> ServiceResult
citesLegal -> LegalCitation
hasFaq -> FAQ
hasChannel -> ServiceChannel
hasFee -> Fee
hasChunk -> Chunk
statesProposition -> Proposition
```

### Department

表示事项主管部门、协同部门或其他实施机构。

属性：

```text
name
departmentId
departmentCode
```

后续可增加：

```text
alias
canonicalName
organizationLevel
regionCode
```

部门层级关系预留为：

```text
Department --belongsTo--> Department
```

但**不能仅凭部门名称自动推断并作为权威事实导入**。当前数据没有可靠的部门层级表，因此第一阶段只发布关系定义，不导入推断层级。

### Material

表示可复用的申请材料。

节点只保留材料的稳定属性：

```text
name
materialId
materialType
sourceType
submissionFormat
```

事项上下文属性放在关系上：

```text
GovernmentService
    -[requiresMaterial {
        required,
        orderNo,
        materialDescription,
        acceptanceStandard
    }]->
Material
```

这样可以避免同一材料在不同事项中的要求互相覆盖。

### ServiceCondition

表示可以独立查询和验证的办理条件。

第一阶段属性：

```text
conditionId
name
description
conditionType
statement
sourceChunkId
confidence
```

其中：

- `description` 保存原始条件文本；
- `statement` 保存经 5W1H 展开的上下文独立陈述；
- `conditionType` 使用受控的粗粒度分类；
- `sourceChunkId` 指向证据 Chunk；
- `confidence` 记录抽取或匹配置信度。

关系：

```text
GovernmentService --hasCondition--> ServiceCondition
```

第一阶段不直接加入复杂的：

```text
operator
logicGroup
conditionExpression
```

这些字段需要通过真实数据抽样后再决定。

### ProcessStep

表示办理流程中的步骤。

属性：

```text
processStepId
name
stepCode
handler
timeLimit
checkStandard
description
```

关系：

```text
GovernmentService --hasProcessStep--> ProcessStep
ProcessStep --nextStep--> ProcessStep
```

步骤在事项内的顺序通过 `hasProcessStep` 关系属性表达：

```text
orderNo: Integer
```

不能把步骤顺序简单写死在共享的 `ProcessStep` 节点上。

### ServiceResult

表示事项办理后产生的结果、批文、证照或通知。

属性：

```text
resultId
name
resultType
description
licenseCode
validityPeriod
```

关系：

```text
GovernmentService --producesResult--> ServiceResult
```

关系属性：

```text
orderNo: Integer
```

### LegalBasis

表示整部法规、规章或规范性文件。

属性：

```text
legalBasisId
name
documentNumber
legalType
issuingAuthority
publishedDate
effectiveDate
lawUrl
```

建议的 `legalType` 受控值：

```text
法律
行政法规
地方性法规
部门规章
规范性文件
其他
```

### LegalCitation

表示某个事项对法规具体条款的引用。

属性：

```text
citationId
article
content
sourceChunkId
confidence
```

关系：

```text
GovernmentService --citesLegal--> LegalCitation
LegalCitation --partOf--> LegalBasis
```

推荐 ID：

```text
LC-{hash(normalized_document_number + normalized_article)}
```

如果同一文号和条款仍然出现多个不同文本，不覆盖原值，应生成冲突记录供审核。

### FAQ

FAQ 保留为结构化实体，不因为部分事项没有 FAQ 就整体舍弃。

属性：

```text
faqId
name
answer
description
orderNo
```

关系：

```text
GovernmentService --hasFaq--> FAQ
```

同时可以把问答转成检索 Chunk：

```text
FAQ.question + FAQ.answer -> Chunk.content
```

这样同时支持：

```text
结构化查询：某事项有哪些 FAQ？
语义检索：用户问题匹配 FAQ 内容
```

### ServiceChannel

表示办理渠道。

属性：

```text
channelId
name
channelType
serviceTime
description
```

关系：

```text
GovernmentService --hasChannel--> ServiceChannel
```

### Fee

表示收费项目和收费要求。

属性：

```text
feeId
name
feeStandard
description
feeStatus
```

关系：

```text
GovernmentService --hasFee--> Fee
```

## 4.2 证据层

### Chunk

Chunk 是原始文本和检索的最小证据单元。

属性：

```text
chunkId
name
content
sourceId
sourceType
sourceField
chunkIndex
serviceId
sourceUrl
sourceFile
sourceLine
```

索引：

```text
content -> TextAndVector
```

`sourceId` 不使用模糊的“所属节点”语义，必须明确指向某个骨架节点 ID。

`sourceType` 用于区分：

```text
GovernmentService
LegalCitation
FAQ
ServiceCondition
ProcessStep
```

`sourceField` 用于区分：

```text
acceptCondition
windowProcess
onlineProcess
checkStandard
legalContent
faq
```

关系：

```text
GovernmentService --hasChunk--> Chunk
LegalCitation --hasChunk--> Chunk
ServiceCondition --hasChunk--> Chunk
```

第一阶段可只导入：

```text
GovernmentService --hasChunk--> Chunk
```

其他来源关系待抽取管线稳定后增加。

### Proposition

Proposition 是开放知识事实的载体，不是固定领域关系的替代品。

建议属性：

```text
propositionId
subjectId
subjectType
predicate
objectId
objectType
objectValue
statement
sourceChunkId
confidence
extractionMethod
extractionModel
extractionVersion
reviewStatus
```

字段使用规则：

- `subjectId`：主体实体 ID；
- `subjectType`：主体类型；
- `predicate`：开放谓词文本，不进入固定关系白名单；
- `objectId`：当客体是已存在实体时填写；
- `objectType`：客体实体类型；
- `objectValue`：当客体是字面量时填写；
- `statement`：完整、上下文独立的自然语言陈述；
- `sourceChunkId`：原文依据；
- `confidence`：抽取或归一置信度；
- `reviewStatus`：审核状态。

关系：

```text
GovernmentService --statesProposition--> Proposition
LegalCitation --statesProposition--> Proposition
Proposition --extractedFrom--> Chunk
```

对于已经有固定关系表达的事实，不重复写入 Proposition。例如：

```text
GovernmentService --handledBy--> Department
```

不再额外生成：

```text
Proposition(predicate="负责办理")
```

除非该命题包含固定关系无法表达的额外限定条件。

## 五、关系域值域约束

Schema 中的关系类型只能定义基本域和值域；具体实例的端点完整性、基数和业务规则由外部约束表校验。

约束文件：

```text
kg/design/constraints.csv
```

建议字段：

```text
relation
source_type
target_type
cardinality
rule
severity
```

初始约束：

```csv
relation,source_type,target_type,cardinality,rule,severity
handledBy,GovernmentService,Department,one-to-many,target_exists,error
collaboratesWith,GovernmentService,Department,one-to-many,target_exists,error
requiresMaterial,GovernmentService,Material,one-to-many,target_exists,error
hasCondition,GovernmentService,ServiceCondition,one-to-many,target_exists,error
hasProcessStep,GovernmentService,ProcessStep,one-to-many,target_exists,error
nextStep,ProcessStep,ProcessStep,one-to-many,no_self_loop,error
producesResult,GovernmentService,ServiceResult,one-to-many,target_exists,error
citesLegal,GovernmentService,LegalCitation,one-to-many,target_exists,error
partOf,LegalCitation,LegalBasis,many-to-one,target_exists,error
hasFaq,GovernmentService,FAQ,one-to-many,target_exists,error
hasChannel,GovernmentService,ServiceChannel,one-to-many,target_exists,error
hasFee,GovernmentService,Fee,one-to-many,target_exists,error
hasChunk,GovernmentService,Chunk,one-to-many,chunk_source_matches_subject,error
statesProposition,GovernmentService,Proposition,one-to-many,subject_matches_subject,error
extractedFrom,Proposition,Chunk,many-to-one,source_chunk_exists,error
belongsTo,Department,Department,many-to-one,no_self_loop;verified_hierarchy_only,warning
```

校验结果不能静默丢弃。建议输出：

```text
valid_rows
invalid_rows
ontology_mismatch_rate
missing_endpoint_count
duplicate_fact_count
conflict_count
manual_review_count
```

违例处理：

```text
严重错误 → 不进入正式图谱，进入 rejects/review 队列
警告 → 可以进入隔离区，同时记录审核状态
```

## 六、实体归一与别名设计

### 6.1 归一顺序

```text
原始名称
    ↓
规则清洗
    ↓
候选别名生成
    ↓
人工确认或高置信自动确认
    ↓
canonical_id
    ↓
写入图谱
```

### 6.2 第一阶段需要处理的实体

```text
Department
Material
LegalBasis
```

### 6.3 不直接自动合并的情况

以下情况不能仅凭字符串相似度合并：

```text
营业执照
营业执照副本
营业执照复印件

省级教育厅
市级教育局
开发区行政审批局

同名法规的不同版本
不同文号的修订文件
```

法规特别要注意：

```text
法规名称相同 ≠ 法规版本相同
文号不同 ≠ 可以直接合并
条款内容不同 ≠ 可以覆盖
```

### 7.3 法律依据转换

当前 `legal_bases.csv` 一行同时包含法规和条款信息：

```text
legal_basis_id
law_name
article
document_number
clause_content
published_date
law_url
```

建议拆分为：

```text
LegalBasis.csv
LegalCitation.csv
GovernmentService_citesLegal_LegalCitation.csv
LegalCitation_partOf_LegalBasis.csv
```

转换逻辑：

```text
law_name + document_number
    -> LegalBasis

normalized(document_number + article)
    -> LegalCitation

service_id + LegalCitation.id
    -> citesLegal
```

原始 `legal_basis_id` 必须保留为来源追踪字段，不能直接丢弃。

## 十二、最终结论

这套设计方法可以采用，但必须遵守以下最终边界：

```text
ZwdmxGJ 是唯一 Namespace
GovernmentService 是唯一核心事项实体
结构化数据优先规则导入
LegalBasis 和 LegalCitation 分层
FAQ 保留实体并可同步生成 Chunk
ServiceCondition 负责可查询条件
Proposition 负责开放长尾事实
Chunk 负责原文证据
Wikontic 负责约束和归一
SocraticKG 负责条件展开
SynthKG 负责长文本命题抽取
```

当前不做：

```text
不直接把所有文本交给 LLM 自动生成 Schema
不凭部门名称推断权威层级
不凭字符串相似度自动合并实体
不把所有长尾谓词做成固定关系
不删除没有被抽取的原始文本
不在没有 1000 + 1000 试点验证前执行全量 LLM 抽取
```

一句话总结：

> **Schema 先建立可验证的 GovernmentService 业务骨架，再通过 Chunk 和 Proposition 承接复杂知识，最后用关系约束、实体归一和来源审核保证图谱质量。**
